## 2. Schema changes (C1 to C16)

| ID | Item | Proposed resolution | Rationale | Owner | Schema impact | Status | Priority |
|---|---|---|---|---|---|---|---|
| C1 | `capabilityType` has no value for a library | Add `library`. Primary type by how it is adopted: **library**, imported or called by code; **tool**, run directly by a person or agent; **framework**, a foundation for building other applications or agents. A capability with several interfaces still gets one primary type | 5 of 16 production capabilities are libraries; they had to be `tool` | Mission 4; Mission 2 confirms (it owns the type list) | Additive (enum value; definitions in the schema description) | **Accepted** 2026-11-16 | P1 |
| C2 | No embedded type for a bundled skill or subagent | Add `skill` and `agent` to `embeddedComponents[].type`. An independently adoptable skill keeps its own manifest under `components` | Caveman's 17 bundled skills and 3 subagents were `other` | Mission 4 | Additive | **Accepted** 2026-11-16 | P1 |
| C3 | No interface type for a CI step | Add `ci_action`: a step in a CI workflow whose inputs form the contract. Not GitHub-specific. Distinct from `capabilityType: workflow`, which says what the capability is; `ci_action` says how it is invoked | Claude Code Action could only say `other` | Mission 4 | Additive | **Accepted** 2026-11-16 | P1 |
| C4 | No cost model for "free software, billed service" | Add `provider_billed`. Structured provider details (provider, billing unit, free tier) are a later enhancement with Mission 1 | 7 of 16 had this pattern: 5 typed `other`, 2 `usage_based` | Mission 4; Mission 1 confirms | Additive | **Accepted** 2026-11-16 | P1 |
| C5 | `platformCompatibility` mixes unrelated dimensions | Narrow `platformCompatibility` to AI hosts and clients, with a controlled list named by the agent that loads the capability: `claude-code`, `claude-desktop`, `codex`, `cursor`, `devin`, `gemini-cli`, `github-copilot`, `windsurf` (VS Code's agent is GitHub Copilot, so `vs-code` is not a value). Add optional `integrations` (uncontrolled kebab-case tokens) for systems, products and frameworks it connects to: forges, CI platforms, `jira-cloud`, `langchain`. Drop languages, runtimes and operating systems: `runtime.detail` already states them with versions, and a real OS restriction goes in `limitations`. This replaces the six-list split with two lists | Of 58 values in 17 manifests, 25 were AI hosts, 13 named connected systems or frameworks, and 20 restated `runtime` or were curator guesses (pdfplumber's provenance: "not stated as a list by the source"). 8 of the 17 lists held no AI host at all | Mission 4, with Missions 1 and 2 | **Breaking** (the host list is now controlled; `schema-compat` reports `ENUM_ADDED`). All 22 manifests migrated and valid: 9 keep host lists, 6 gain `integrations`, 7 lost only repeated or guessed values | **Accepted** 2026-11-16 (applied; hosts named by agent). Add `devin` only to manifests whose sources name it | P1 |
| C6 | `dependencies` only references other manifests, so every production manifest says "none" | Keep `dependencies` for one concept: other **registered capabilities**. The other two concepts now have structured homes: what the adopter installs or configures is `setup` (with `kind`: `software`, `system_package`, `account`, `env_var`, C7); the runtime is `runtime`; the systems it works against are `integrations` (C5). The definition says so | Phase 1 testing (2026-11-16): every external dependency the field review found (Chrome, Docker, poppler, a model API, a Jira site) is now stated in `setup`, `runtime`, or `integrations` in the 22 manifests. The split is no longer needed | Mission 4; Mission 3 for third-party dependencies | None (description only; `schema-compat`: annotation) | **Accepted** 2026-11-16 (clarification instead of the breaking split) | P1 |
| C7 | `setup` does not say what kind of item each entry is | Add optional `setup[].kind`, nine values. `system_package`: installed by the operating-system package manager; `software`: other installed software or runtime, such as a browser or a language package. `kind` classifies the item; `required` and `secret` stay separate | 11 of 40 setup items are not environment variables | Mission 4, with Mission 5 | Additive | **Accepted** 2026-11-16 | P1 |
| C8 | Trust facts (write access, telemetry, data egress) exist only as free text | Do not add fields unilaterally. Send Mission 3 the evidence and candidate categories: permissions, data egress, telemetry, credentials, third-party services, model usage | Write access by default in 4 capabilities, telemetry in 2, data sent to a provider in 7 | **Mission 3** defines requirements; Mission 4 then represents them | Additive later | **Deferred to 0.2** (2026-11-16, answered for Mission 3): trust facts stay in `limitations` for 0.1 | P2 |
| C9 | `source` repeats a `repository` publication | `source` is the canonical origin. `publications` lists distribution channels, including a repository only when people install or run the capability directly from it (Agent Skills, GitHub Actions) | 8 of 22 manifests repeat the repository; Phase 1 testing (T6) found no double counting and no false link in 66 identity cases, so the repetition is a legitimate channel, not a duplicate fact | Spike 3 (this is U2) | None to the structure; descriptions and a new warning `PUBLICATION_REPEATS_SOURCE` | **Accepted** 2026-11-16: option A with five rules ([analysis](phase-1-testing/c9-source-and-publications.md)) | P1 |
| C10 | A repository-wide license is always flagged for review | Keep the check. Let a curator close it by confirming the scope through `provenance[].confirmedBy`, with a rule for who may confirm | 7 of 22 flagged, including single-package repositories | Mission 4; Mission 5 for the confirmation workflow | None (validator and workflow) | **Accepted** 2026-11-16: the owner or a Mission 5 curator confirms through `provenance[].confirmedBy`, which closes `LICENSE_NEEDS_REVIEW` | P2 |
| C11 | Several dates with different meanings | Define them: `lastUpdated`, when the manifest was last edited; `provenance[].observedAt`, when the evidence was read; `publications[].updatedAt`, when the channel last changed. Warn when evidence is older than a defined freshness threshold, not merely older than `lastUpdated` | Manifests are updated using evidence read earlier; 2 of 22 carry older ids | Mission 4 | None (definitions and a validator warning) | **Accepted** 2026-11-16: evidence older than 180 days raises `EVIDENCE_STALE` (warning) | P2 |
| C12 | One capability supports different platforms in different publications, but `platformCompatibility` exists only for the capability as a whole | Add optional `publications[].platformCompatibility`, with the same tokens as the capability-wide list. It is never inherited from the capability-wide list; omitting it means not provided. When a publication names hosts, the capability-wide list is required (a conditional rule, added 2026-11-16, so that a consumer filtering on it finds the capability), and it must contain every host a publication names, checked by a new `PLATFORM_COMPATIBILITY_MISMATCH` warning. Each publication's list needs evidence for that artifact | Proposed in the Mission 2 standards draft (§4.4). In the 22 manifests: Chrome DevTools MCP's marketplace entry installs only into Claude Code while its npm package also works in Cursor, VS Code and Gemini CLI; PR-Agent's GitHub Action runs only on GitHub Actions | Mission 4; Mission 2 confirms | Additive (optional field; `schema-compat`: 22 of 22 manifests still valid) | **Accepted** 2026-11-16; the capability-wide list, its conditional rule, and `PLATFORM_COMPATIBILITY_MISMATCH` were then **superseded by C14** (hosts are stated per publication only) | P1 |
| C13 | `setup` cannot express alternative items ("a Cloud token *or* a Data Center token") | Add optional `setup[].group`: items that share a group are one alternative; an adopter supplies the required items of one group. A single group raises `SETUP_SINGLE_GROUP` | Phase 1 testing (T8): MCP Atlassian marks all three Jira credentials `required: false` because they are alternatives; Exa states "OAuth or API key" as one item. In all, 5 of 22 have alternative credentials (also Claude Code Action, GitHub MCP, Tavily MCP); all 5 now use groups | Mission 4, with Mission 5 (submission form) | Additive | **Accepted** and applied 2026-11-16 | P2 |
| C14 | The capability-wide `platformCompatibility` repeats the publications' lists | Remove it, with its conditional rule and `PLATFORM_COMPATIBILITY_MISMATCH`. AI hosts are stated only in `publications[].platformCompatibility`; a capability supports the union of its publications' hosts. A capability used from its repository states hosts on a repository publication with its ref. `x-retiredFields` tells an author where to move the value | By C12's rule, the top-level list was the union of the per-publication lists: one fact stored twice, with two rules that existed only to keep the copies in sync. In 6 of the 9 manifests with a list, it hid which publication works in which host (Chrome DevTools' marketplace entry only in Claude Code; Tavily's Claude Code support only on the hosted endpoint). [Analysis](phase-1-testing/field-overlap-review.md) §2 | Mission 4, with Missions 1 and 2 | **Breaking** (`FIELD_REMOVED`; 0.1 is unpublished). 9 manifests moved their hosts to 13 publications, re-checked against the READMEs (25 values became 36; Tavily's undocumented `github-copilot` removed) | **Accepted** 2026-11-16 (Mission 4 team) | P1 |
| C15 | `intendedAudience` restates other fields | Remove it. The audience is read from `supportedUseCases` and `description`; `x-intendedAudience` keeps a value as an extension. A controlled role vocabulary can be proposed for 0.2 with the functional classification (U5) if Missions 1 or 2 need to filter by role | 25 of 25 values in 16 manifests restate the description, use cases, runtime, or integrations, or say only "developers" (7 uses); none has provenance; only a helpful J1 question used it; not a search field. [Analysis](phase-1-testing/field-overlap-review.md) §3 | Mission 4; Mission 2 (it listed the audience in its scope) | **Breaking** (`FIELD_REMOVED`; 0.1 is unpublished). 16 manifests and 4 examples migrated | **Accepted** 2026-11-16 (Mission 4 team, answering for Mission 2) | P1 |
| C16 | `runtime[].detail` repeats publications | Keep `runtime` (a capability without publications still runs somewhere; `assessable` needs it), but its detail states only what the environment requires or who operates it. New warning `RUNTIME_REPEATS_PUBLICATION` when a detail names a publication's locator, package name, or native name | 24 of 32 details repeated a package or install command (15), an image (5), or the hosts or endpoint (4); one pinned a version that `nativeVersion` records. The warning flags 18 of the 24 automatically. [Analysis](phase-1-testing/field-overlap-review.md) §4 | Mission 4 | None structurally (definition and a warning) | **Accepted** and applied 2026-11-16: 24 details corrected, 0 warnings | P2 |

## 3. Open questions (U1 to U10)

| ID | Question | Proposed resolution | Evidence so far | Owner | Schema impact | Status | Priority |
|---|---|---|---|---|---|---|---|
| U1 | Completeness levels instead of a fixed mandatory set? | Keep the levels. Mission 4 calculates and reports the level; each consuming process sets its own required level. A level never means approval | 22 real manifests split cleanly: 17 adoptable, 5 assessable, with the missing facts named | Mission 4, with Missions 1, 2, and 5 | None | **Accepted** 2026-11-16, with U9: the levels stay; listing requires `adoptable` | P1 |
| U2 | Fold `source` into `publications`? | Decide together with C9 | 8 duplicates in 22 manifests | Spike 3 | Possibly breaking | **Accepted** 2026-11-16 with C9: `source` stays; it is not folded into `publications` | P1 |
| U3 | Identifier format, and who allocates namespaces? | Mission 5's workflow assigns the id when a submission is accepted. The namespace comes from a registered list of products, domains, and verified publishers kept by Mission 2. Ids are unique across the catalogue, never change, and are never reused; a fork or a renamed repository keeps or gets an id by these rules, never from its URL | Curators chose every id in the 22 manifests; nobody allocated them. Stored repository ids survived a repository move (PR-Agent) | Spike 3, with Missions 5 and 2 | Possibly a pattern change | **Accepted** 2026-11-16 by the Mission 4 team (answered for Missions 5 and 2); awaiting confirmation by Missions 5 and 2 | P1 |
| U4 | Is a configuration-only wrapper its own inventory entry? | A configuration-only wrapper is its own record, linked to what it wraps by `relations` type `wraps` (the validator already follows a wrapper's link for lifecycle warnings). It is not a publication of the original, because its owner, version, and configuration differ | Research cases only (for example a plugin that only configures an MCP server) | Spike 2, with Mission 2 | Possibly a `relations` rule | **Accepted** by Mission 4 on 2026-11-16; Mission 2 to confirm | P2 |
| U5 | Which abilities vocabulary, if any? | Work with Missions 1 and 2. Do not adopt the model-benchmark CSV vocabulary, which describes model skills, not adoptable capabilities | `inputs` and `outputs` were stated for only 4 and 1 of 16 production manifests | Spike 2, with Missions 1 and 2 | Additive later | **Accepted** 2026-11-16: no new ability field in 0.1 (four existing fields); Mission 2's functional classification becomes a field in 0.2, cross-walked to OASF ([analysis](phase-1-testing/abilities-vocabulary-analysis.md)) | P2 |
| U6 | How are owner lifecycle declarations constrained? | Keep `lifecycleStatus` optional and owner-declared. Keep observed status (`source.status`, `publications[].status`) separate. Get Mission 3's agreement on the transition rules | No owner declared a lifecycle in 22 manifests; the observed status always carried the signal | Spike 3, with Mission 3 | None | **Accepted** 2026-11-16 (answered for Mission 3): the transition table as proposed | P2 |
| U7 | Publish as an AI Catalog entry type, or only convertible? | Evaluate interoperability (can a consumer use both without loss?), not just conversion | Not tested by this set; Phase 1 Ticket 1 | Spike 1 | Unknown | **Accepted** 2026-11-16: interoperable by the hybrid projection (native artifacts plus the manifest in `extensions`), not a new entry type ([test](phase-1-testing/ai-catalog-interoperability.md)) | P2 |
| U8 | What curation effort per capability is acceptable? | Measure it. Design the contribution UI so contributors confirm suggested values instead of typing every field | 241 provenance entries in 22 manifests (about 11 each), 67 curated; time not measured | Mission 4, with Mission 5 | None | **Open** | P2 |
| U9 | Do Missions 1 and 2 accept partial records? | A record is listed in the catalogue only at `adoptable` or `governed`. Records below that are kept for enrichment, with their missing facts reported, but not listed or recommended | Not answered | Missions 1 and 2 | None | **Accepted** 2026-11-16 (answered for Missions 1 and 2). All 22 manifests now reach `adoptable` | P1 |
| U10 | Is "declared none" owner-asserted only, or verifiable? | Distinguish owner-confirmed absence from a curator's assumption, through `provenance[].method` and `confirmedBy` | `setup: []` for 3 libraries and `dependencies: []` for 16 were curator assertions; the dependency one is misleading (C6) | Spike 2 | None | **Accepted** 2026-11-16 (answered for Mission 5): owner or curator confirms through `confirmedBy`; owner preferred for `setup` and `limitations` | P2 |
